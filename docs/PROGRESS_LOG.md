## Step 38 — the database boundary
**Date:** 2026-11-10  **Status:** done
**Built:** `scripts/migrate-oracle.ts` (role `oracle_reader` NOLOGIN, schema `oracle` with ten explicit-column views each with a `COMMENT`, grants, `oracle_log` + index); `oracle_log` added to `src/db/schema.ts` so the local bootstrap builds it; `db:migrate-oracle` script and the `--test` call added to the `db:test-migrate` chain in `package.json`. The AGENTS.md re-run line was already present from the docs commit.
**Decisions:** the migration also runs `REVOKE ALL ON ALL TABLES IN SCHEMA public FROM oracle_reader` — a no-op today, but it erases any stray grant from an earlier experiment on the next run. `VIEWS` is deliberately **not exported**: the script runs `main()` on import, so importing it from the step 40 test would run the migration. That test should read the views from the database (`information_schema`), not from this file.
**Learned:** `SET LOCAL ROLE oracle_reader` as the first statement of a `sql.transaction([...], { readOnly: true })` batch DOES take effect through the local proxy (`current_user` reads `oracle_reader` inside it). This was untested going in. The role needs no grant on any base table: views run with their owner's privileges, which is how it can read `oracle.managers` while `public.managers.pin_hash` is refused. The refusal text depends on the database: local (`public` rebuilt by bootstrap, no PUBLIC grant) says `permission denied for schema public`; with `USAGE` on `public` granted to PUBLIC, as on Neon, it says `permission denied for table player_queue`. Step 39 must not match on either wording. Also: `CREATE TABLE oracle.x` inside the `readOnly` batch fails on "read-only transaction" *before* any permission check, so the roadmap's fourth check does not prove the role cannot write. I also ran it with `readOnly: false` and got `permission denied for schema oracle`, which does.
**Watch out for:** (1) `db:local:setup` drops `public` and with it every view, but the role and the empty `oracle` schema survive — re-run `db:migrate-oracle` every time. (2) Local data has no history imported, so most views count 0 rows; only `managers` (10) proves anything about content. (3) `numeric` columns (`points`, `price`-adjacent totals) come back as strings from Neon, so step 39's runner returns strings for every points column. (4) `npm run local --` is what keeps `dotenv -e .env.local` from pointing the script at Neon; the local DB is also named `neondb`, so the script's "in neondb" banner cannot tell you which one you hit. (5) The roadmap's other view columns all matched `schema.ts`; no name disagreed.

## Step 39 — the SQL guard and the read-only runner
**Date:** 2026-11-10  **Status:** done

Verified. (3) The 201st row is dropped and `truncated` set only when 201 come back, so exactly 200 rows is not truncated (tested). (4) Refusal wording differs local vs Neon; assert `ok === false`, never the text. (5) Points columns arrive as strings.

## Step 48 — seed distribution and leverage
**Date:** 2026-11-11  **Status:** done
**Built:** `playoffOdds()` now also returns `seedPct` (share of simulations finishing in each seed) and `leverage` (`{ ifWin, ifLose }`, playoff odds among simulations where the team won, and lost, its next scheduled game; null when no game remains); an "If W / L" column and a ten-cell seed strip in `PlayoffOddsPanel`, both through `formatOdds`; glossary entries `odds-leverage` and `seed-strip`. `playoff-odds.test.ts` 29 tests; unit suite 595.
**Decisions:** a tie on a fixture counts toward neither leverage group (it cannot occur with continuous scores, but it is not a win). Leverage is null if either group is empty in the sample, rather than printing a number computed from nothing. "Next game" is the fixture in the earliest remaining week.
**Learned:** the hard constraint is provable, not just believable. The pre-change outputs were captured to `src/lib/__fixtures__/playoff-odds-baseline.json` (four fixtures, full precision) BEFORE editing the model; the test asserts strict equality on `playoffPct`, `byePct`, `projectedWins`, `remainingSos`, `rating` AND row order. And `npm run local -- npm run odds:backtest` prints the identical Brier before and after: 0.159 model, 0.192 history, 0.240 flat guess, every bucket the same. Leverage behaves as it should on real data (2025 stood in at week 8): bubble teams swing hard (Daniel 62% if he wins, 30% if he loses), locks barely move (Justin >99% vs 97%), eliminated teams barely move (Bolek 3% vs <1%).
**Watch out for:** (1) Leverage is the difference between two observed groups, not a causal effect: a win is also evidence the team is strong, so it overstates what the one game changes. The glossary says so. (2) The seed strip shades by the square root of the share so a 5% seed stays visible; the exact shares are in its aria-label and hover title. (3) Do not move any draw on `rand`; see the new AGENTS.md rule.

**Built:** `titlePct` per manager; `bracketOrder()` (exported) and an internal `playBracket()`; a "Title" column; glossary entry `title-odds`. Tests for the sum, the zero case, determinism, a four-team field and the bracket layout.
**Decisions:** the bracket is **fixed, not re-seeded**. The roadmap said to confirm. Seeding 2025 from `matchups-*.json` by wins then points for gives seeds 1-6 as rosters 6, 10, 9, 2, 4, 3; the bracket played 2 v 4 (seeds 4 v 5) and 3 v 9 (seeds 6 v 3), and then roster 6 (seed 1) met the winner of 4 v 5, which was roster 4, a 5 seed. Re-seeding would have given the top seed the 6. The generic layout (`bracketOrder`) is `[1, 8, 4, 5, 2, 7, 3, 6]` with adjacent slots meeting, and seeds past the field are byes. Playoff games use the same model (two draws around each team's simulated true rating) from a SEPARATE generator seeded `(season * 100 + week) ^ 0x5bd1e995`, so the regular-season stream is untouched.
**Learned:** title odds sum to 1 across the league and a team with `playoffPct` 0 has exactly 0, both asserted. On the 2025 stand-in at week 8 the two bye-holders lead (Mario 29%, Justin 22%) and the bottom two are under 1%. `formatOdds` correctly prints "<1%" rather than "0%" for them while games remain.
**Watch out for:** (1) Title odds have NOT been backtested against actual champions the way playoff odds have; seven bracket games a year gives far too few to calibrate a probability, so treat it as a fair-model number, not a validated one. (2) The fixed bracket is correct for `playoff_seed_type: 0` in 2025's league settings; if the league ever turns re-seeding on, `playBracket` is the one place to change. (3) `PlayoffOddsRow` gained three required fields; anything constructing one by hand must supply them.

## Step 50 — the positional scorecard derivation
**Date:** 2026-11-11  **Status:** done
**Built:** `src/lib/positional.ts` (`positionalScorecard`, `memberPositional`, `POSITIONS`) + `positional.test.ts` (12); `getPositionalScorecards()` in `src/server/history-service.ts`.
**Decisions:** `positions` lists only positions present in the data, so there is no empty K column (this league has never started a kicker: QB, RB, WR, TE, DEF only), while K stays supported for a league that does. A position this league does not play, or a null one, goes to an `unknown` bucket that is reported on the manager and counted league-wide (`unknownRows`), so positions plus unknown always equal the started total. A manager who started nobody at a position counts as 0 in that position's mean rather than being excluded. The loader restricts to regular-season weeks that are also COMPLETE; `regularSeasonWeekKeys` alone would count a half-played week of the season in progress for some managers and not others.
**Learned:** the data confirms why the roadmap says never to group on slot. `player_weeks.slot` holds nonsense for this purpose: RBs recorded in a "WR" slot, TEs in a "QB" slot, so a slot-based scorecard would be wrong at the source, and the test feeds an RB with slot "WR" to prove it is ignored. Real-data check across all six weekly seasons (local Postgres): every manager's started points summed from `player_weeks` equal their regular-season team score from `season_matchups` to within 0.00, the week counts are 14 (13 in 2020), there are zero unknown rows, and the per-position differences sum to zero within 1e-12. That equality is a strong end-to-end check that the importer, the week filter and the grouping all agree.
**Watch out for:** (1) Totals, not per-week averages, so a season in progress is compared only against the same weeks of the same season; never compare a part-season grid with a full-season one. (2) `diff` is unrounded in the data; round at display only, or rounded cells stop summing to zero. (3) Do not add a cross-position ranking ("best at QB vs best at WR"): it measures nothing, see the positional.ts header.

## Step 54 — top-ten lists behind every record
**Date:** 2026-11-11  **Status:** done
**Built:** `recordLists(input, top = 10)` in `src/lib/history.ts`; the Records page shows a `<details>` "Top 10" under every single-game and season record (rank, value, manager, week, season, opponent). 7 new tests (suite 628).
**Decisions:** the roadmap said to derive both from the same sorted rows, so `records()` itself was refactored: a private `recordRankings()` ranks every candidate for each single-game and season record, `records()` takes entry one, `recordLists()` takes the first ten. The holder therefore cannot drift from the head of its list, and a test asserts `lists[key][0]` equals the record for every key. Streaks list one best run per manager-season, because that is the grain `longestStreaks()` already works at (a manager's two 7-win runs in one season would not both be listed). Careers have no list: they are one row per manager already.
**Learned:** the refactor is behaviour-preserving: every existing `records` test still passed untouched. My first `streakRuns` was a subtle bug the tests did not catch by themselves: it skipped ties instead of treating them as a break in the streak, and did not exclude playoff games, both of which `longestStreaks()` does; caught by re-reading the original. Ranking uses a stable sort, which is what keeps "ties keep the earliest, so a record has one holder" true; a test pins it. Separately found and fixed an existing phone layout bug on this page: the three-column grid and the season cards had no `min-w-0`, so at 390px the first column's non-wrapping badges stretched the whole page to 1067px and clipped every value on the right. Adding `min-w-0` to the grid sections and the review card fixed it.
**Watch out for:** (1) The page is still marginally wider than the phone because of the screen-reader-only chart tables (`ChartTable`, `sr-only`) in the season cards; visible content fits, but it is worth a look on a real device. (2) A top-ten shows ties at their sorted position without a shared rank number. (3) `recordLists()` recomputes coverage and finished standings itself; if `records()` setup changes, change both (they share `recordRankings()`, so only the setup is duplicated). (4) Playoff lists hold few rows before more seasons exist; fewer than ten is normal, and a one-entry list shows no details control.
